# Устройство и выпуск интеграции

## Модули

- `client.py`: aiohttp-клиент страницы и таблиц, ограничение ответа 2 МБ, timeout 25 секунд, проверка HTTP и UTF-8.
- `parser.py`: разбор HTML без исполнения JavaScript; metadata, наблюдения, forecast и интервальные осадки.
- `search.py`: GET `/mobile/location/jsonsearch.php`, сохранение подписей региона и станции, проверка адресов.
- `config_flow.py`: название → выбор → проверка данных → unique_id точки. В config entry сохраняется только канонический URL.
- `__init__.py`: общий DataUpdateCoordinator, первый refresh, загрузка weather/sensor и listener опций.
- `weather.py`: наблюдения отдельно от прогноза, кеш hourly и обновление подписчиков карточек.
- `sensor.py`: timestamp успешного получения данных.

Не менять domain `rp5_weather`, VERSION формы `1` или суффиксы unique_id при правках упаковки.
Разделение кода по модулям не должно менять запись HA, сущности или частоту сетевых обращений.

## Контракт RP5

Время страницы — локальное; `gmtAdd` задаёт смещение UTC и перечитывается каждый цикл, включая возможную смену DST.
`page_values.id` задаёт ID точки. Поиск отдаёт JSON-массив с `id`, `name`, `namealt`;
используем проверенную страницу из `namealt`, окончательный unique_id получаем из самой страницы.

POST `/mobile/location/html_forecast.php`: `id`, `ftab=2` для прогноза, `ftab=0` для наблюдения.
Ответ — JSON-строка с HTML, несмотря на content-type text/html.
Referer страницы места обязателен: без него наблюдался HTTP 200 с пустым телом.

Даты сопоставляются с группами часов между переходами через полночь; шаг должен быть 1 или 3 часа.
Дата каждой группы обязана совпадать с последовательными календарными заголовками.
Сумма `colspan` проверяется с учётом двух служебных колонок, однако правая служебная
колонка может ошибочно учитываться RP5 в предпоследней дате. Нельзя исправлять это
сортировкой уже неверно датированных точек или удалением повторов.

Во время работы coordinator вызывает `fetch(allow_partial=True)`: запросы наблюдения и
прогноза проверяются независимо. Если доступна хотя бы одна часть, она публикуется,
а отказ другой виден в атрибутах и WARNING при смене ошибки. Неисправная часть очищается,
старый прогноз и устаревшие наблюдения не выдаются за свежие. Время `Данные получены`
относится к последнему обновлению с хотя бы одной пригодной частью. Полный отказ остаётся
`UpdateFailed`. Добавление и перенастройка через config flow используют строгий режим:
корректный прогноз по-прежнему обязателен.

Количества осадков находятся в onclick-подсказке иконки. Вода в мм и снег в см — разные величины.
Часовая интенсивность умножается на подтверждённую длительность; уже накопленное количество не умножается повторно.
Неизвестные количества / интервалы пропускаются. Последующие трёхчасовые интервалы не интерполируются.

## Релиз

Если используется частное зеркало, его адрес и локальные доступы хранятся отдельно от публичного кода.
Публичная репа: `git@github.com:konstantinhidirov/ha-rp5-weather.git`.
В обеих репах должна быть одна история коммитов; приватные настройки HA хранятся отдельно.

1. Измени код и тесты; увеличь `manifest.json.version`, обнови CHANGELOG.
2. Запусти тесты, отправь один и тот же коммит в main обеих реп.
3. Дождись успешных проверок GitHub HACS, hassfest и тестов.
4. Создай tag `v<version>` на проверенном коммите и отправь его в обе репы.
5. Push тега запускает workflow: hassfest, тесты, упаковка и публикация GitHub Release с `rp5_weather.zip`.
6. Дождись появления архива в релизе; затем HACS → Обновить информацию → обновить и перезапустить HA.
7. Проверь loaded, прежние сущности, timestamp, weather.get_forecasts hourly и ошибки RP5.

Сборка пакета вручную:

```sh
python3 scripts/build_release.py
```

В `dist/rp5_weather.zip` файлы лежат относительно корня интеграции (`manifest.json`, `weather.py`, `brand/` и т. д.).
Пакет не содержит tests, документацию репы, домашние данные или SSH-ключи.
HACS распаковывает этот формат в `custom_components/rp5_weather`.

Для отката скачай предыдущую версию через HACS и перезапусти HA. Запись HA и сущности не удаляй.
Для перевода ручной установки под HACS достаточно скачать файлы в тот же домен и перезапустить HA.

## CI и проверка

HACS и hassfest — официальные валидаторы, запускаемые на GitHub. Не обходить неуспешные проверки через ignore.
HACS Action требует topics, description и issues; эти поля настраиваются в GitHub, а не в Git.
Тесты запускаются с настоящими классами HA внутри закреплённого контейнера Core 2026.10.1.
Config flow tests создают отдельный объект HA во временной директории, не создают реальных записей или сущностей.
Live-запросы не входят в CI: изменения погодных данных не должны делать тесты случайными.
